fixtures, temporary files, substituted transports, and real localhost HTTP
servers. It never contacts Blizzard or reads the user's account configuration.

workflow targets Node 22 and 24 on Linux and Windows. The published initial release

script are included in the package.

## Live account result and its limits

Live modern enrollment succeeded on 2026-09-18 through the original manual flow.
After that authenticator was removed, a fresh enrollment succeeded through the
automatic localhost callback and browser confirmation. The first confirmation
attempt exposed a referrer-policy bug, now fixed and reproduced in Chromium with
a synthetic token. The stale login token was then rejected with HTTP 401; a fresh
sign-in completed token exchange, attachment, and local recovery/config storage.
The saved secret was exported as an OTPAuth URL containing `digits=8`. No personal
serial, token, secret, recovery file, or 1Password item is included in this source
package.

The integrated result page was subsequently tested with synthetic enrollment
responses in Chromium and the automated suite. No additional real authenticator
was attached for that UI change. Its README screenshot contains public test data.

These enrollments do not establish support across all account states,
regions, or future service changes. No successful login using a code generated by
1Password was observed, and no automated vault update was confirmed.

In-game benefits, including extra WoW backpack slots and the Core Hound Pup, were
not tested. The README links Blizzard's eligibility guidance separately from the
project's verified enrollment results.

The original Python library uses a separate unauthenticated binary enrollment API.
The `enroll` command implements the newer browser/SSO/JSON flow described in
[upstream issue #42](https://github.com/jleclanche/python-bna/issues/42).
[Issue #38](https://github.com/jleclanche/python-bna/issues/38) reports the legacy
HTTP 502 behavior. These are distinct paths; passing legacy protocol fixtures
does not establish live legacy service availability.

## Readability refactor

The local sign-in HTML and CSS now live under `web/`. The browser launcher, template
renderer, and HTTP receiver have separate responsibilities. Enrollment has four
numbered steps, names explain token and byte-buffer roles, and protocol comments
explain the required bit operations and legacy packet layouts. Source files and
tests use consistent formatting without introducing a runtime dependency or build
step. [ARCHITECTURE.md](ARCHITECTURE.md) maps every module and follows sensitive data
through the application.
